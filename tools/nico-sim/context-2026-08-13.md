# nico-sim context — 2026-08-13

## Managed Host OOB Routing — underlay_local vs overlay_evpn

### Background

During MAT testing on the ytl site we discovered that Nico-api (running on CP VMs)
could not reach the BMC mock addresses (9.140.2.x) that MAT binds to on the
sim-host's `br-dc1-internet` bridge.

**Root cause**: `leaf-mat` needs a connected route for the `rack-mat-hosts` prefix
(9.140.2.0/24) so FRR can advertise it into BGP and the rest of the fabric can
route to it. Without a gateway IP on `leaf-mat:eth3`, FRR never advertises the
prefix and Nico-api times out trying to reach the BMC mocks.

### Architecture — production SMN (from startupSMN.template)

Production DPU (BlueField) uses a dedicated VRF `vpc_{ControlPlaneVNI}` (e.g.
`vpc_60000`) configured via NVUE. The relevant paths:

1. **Leaf (ToR) → EVPN**: rack underlay prefixes exported into EVPN as type-5
   routes with RT `{DatacenterASN}:900` (`FnnCommonManagedNodeBmcRouteTarget`).

2. **DPU VRF import**: `vpc_{ControlPlaneVNI}` imports RT `{DatacenterASN}:900`
   from EVPN so BMC prefixes land in that VRF.

3. **Bidirectional route leak**: `vpc_{ControlPlaneVNI}` ↔ `default` VRF. Routes
   imported from EVPN are accessible to Nico-api in the default VRF on the CP host.

4. **DPU → Leaf**: DPU exports its own routes (site-controller loopback, MetalLB
   service IPs) into EVPN with RT `{DatacenterASN}:{FnnCommonSiteControllerRouteTarget}`
   (RT 50100) for SMN return traffic.

### Config option added: `oob_routing_mode`

Added under `managed_hosts:` in site yaml:

```yaml
managed_hosts:
  oob_routing_mode: underlay_local   # underlay_local | overlay_evpn
```

### underlay_local (IMPLEMENTED)

Simple. At ContainerLab deploy time, `leaf-mat:eth3` gets the gateway IP for the
MAT underlay prefix via a startup exec command:

```
ip addr add 9.140.2.1/24 dev eth3
```

This creates a connected route so FRR can advertise `9.140.2.0/24` via regular BGP.
The fabric learns the route: leaf-mat → spine-1/2 → super-spine → DPU stand-in →
CP VM. Nico-api can then route to 9.140.2.x via the fabric.

No changes to DPU FRR config required.

**Files changed**:
- `generate-fabric.py`: load `oob_routing_mode` + `mat_gateway_ip` from yaml;
  add exec cmd for leaf-mat when mode = underlay_local
- `nico-sim.yaml`: add `oob_routing_mode: underlay_local` under `managed_hosts`

### overlay_evpn (NOT YET IMPLEMENTED)

Matches the production SMN architecture. Requires:

**leaf-mat changes** (`generate-fabric.py`):
- Create VRF `bmc` with L3VNI 900 in FRR
- Add gateway IP (`9.140.2.1/24`) to an interface in that VRF
- Configure BGP EVPN to export routes from VRF `bmc` with RT `{datacenter_asn}:900`
- Independent of underlay_local code path (no shared functions)

**DPU stand-in changes** (`generate-nodes.py`, `gen_dpu_frr_conf`):
- Create VRF `vpc_{ControlPlaneVNI}` (e.g. `vpc_60000`) in FRR
- Assign VXLAN VNI `{ControlPlaneVNI}` to it
- Import from EVPN: RT `{datacenter_asn}:900` into `vpc_{ControlPlaneVNI}`
- Bidirectional route leak: `vpc_{ControlPlaneVNI}` ↔ default VRF
- BGP neighbor with CP host VM inside the VRF (for SMN return path)
- Independent of underlay_local code path

**Key FRR constructs needed** (overlay_evpn, DPU stand-in):
```
vrf vpc_60000
 vni 60000
!
router bgp {dpu_asn} vrf vpc_60000
 address-family ipv4 unicast
  import vrf default
  import vrf route-map ALLOW_ALL
 address-family l2vpn evpn
  advertise ipv4 unicast
  route-import from-evpn route-target {dc_asn}:900
  route-import from-evpn route-target {dc_asn}:901
  ...
!
router bgp {dpu_asn}
 address-family ipv4 unicast
  import vrf vpc_60000
```

**Key FRR constructs needed** (overlay_evpn, leaf-mat):
```
vrf bmc
 vni 900
!
interface lo vrf bmc
 ip address 9.140.2.1/24
!
router bgp {leaf_mat_asn} vrf bmc
 address-family l2vpn evpn
  advertise ipv4 unicast
  route-target export {dc_asn}:900
```

### Deployment order

Both modes require `deploy-fabric.py` to be re-run (regenerates topo.clab.yml with
the exec cmd). The running leaf-mat can be patched without full redeploy:

```bash
# Quick patch for underlay_local on running system
docker exec clab-dc1-leaf-mat ip addr add 9.140.2.1/24 dev eth3
# Verify FRR picks up the connected route:
docker exec clab-dc1-leaf-mat vtysh -c "show bgp ipv4 unicast 9.140.2.0/24"
```
